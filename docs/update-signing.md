# Portable P2P update trust policy

The Windows portable build in PeerSync uses **unsigned P2P executable updates**.
A release signing seed is not required, `PSN.exe.update.json` is not required,
and `scripts/build-portable-win.ps1` does not sign the generated executable.

## Trust boundary

An executable update is accepted only from a remembered peer that is marked
locally as `mine`. The sender advertises the executable size and SHA-256. The
receiver checks both after download, and the Python updater checks the staged
executable again immediately before replacement.

This is an integrity check inside the remembered-device trust boundary; it is
not publisher authentication. That trade-off is intentional for PeerSync.

## Runtime signature compatibility

The signature verification helpers remain available for compatibility with
older/signed metadata, but signing is **not** a prerequisite:

- no pinned public key -> `signatureRequired=false`;
- pinned public key + normal mode -> a valid signature is required;
- pinned public key + explicit unsigned mode -> `signatureRequired=false`.

The production portable build generated by `build-portable-win.ps1` embeds an
empty update signing key and `ALLOW_UNSIGNED_UPDATE = True`, therefore it uses the
unsigned remembered-`mine` + size/SHA-256 path.


## Sidecar schema naming

New PeerSync signature sidecars use `schema: peersync-update-v1`. The runtime still
accepts the historical schema exposed as `LEGACY_UPDATE_MANIFEST_SCHEMA` **for verification/migration only**
so already-produced signed metadata is not invalidated. New build/signing scripts do
not emit the legacy schema. This compatibility identifier is not product branding.

## Release identity in update metadata

Update metadata carries the product version (`buildLabel`, the date-only
`DDMMYY` label) and the monotonic within-day `releaseRevision`; see the
versioning and releasing sections of the README. The revision participates in
update ordering on both sides, so two different official builds of the same
date are distinguishable.

The release revision is **not** part of the signed payload. A sidecar without
`releaseRevision` predates the revision identity and is still accepted; one that
carries it must agree with the launcher's own compiled revision before it is
allowed to describe the executable bytes. The published SHA-256 remains the
integrity authority for the exact bytes.
